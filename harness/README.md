# harness — детерминированный слой харнесса Claude Code

TypeScript под Node ≥ 24 без сборки и без `node_modules`. Зачем контур и как он разложен — корневой `README.md`
репозитория; здесь — устройство слоя, выключатели, границы и проверки.

## Подключение

```bash
sh harness/install.sh                # найти Node >= 24, поставить тулчейн TypeScript, если его нет, записать ~/.claude/env/harness.env, симлинк ~/.claude/harness
sh harness/install.sh --ensure-node  # Node >= 24 нет — скачать официальную сборку в ~/.claude/env/node/<версия>/ (sha256 сверяется);
                                     # PATH, nvm и системный node других проектов не трогаются
~/.claude/harness/bin/run scripts/toolchain.ts --install   # то же отдельно: TypeScript ровно по TOOLCHAIN.lock (integrity + sha256), кеш ~/.cache/claude-harness
```

Сессия в репозитории всегда под харнессом: `.claude/settings.json` подключает события через шим
`.claude/bin/hook`. Шим отдаёт событие user-level харнессу, только если `~/.claude/settings.json` привязывает
именно это событие к `harness/bin/hook` (один `grep`); иначе запускает харнесс чекаута сам — одного симлинка
`~/.claude/harness` для отказа мало, его ставит и авто-установка Node. Тот же файл задаёт
`CLAUDE_HARNESS_AUTO_NODE=1`: на старте сессии без Node ≥ 24 или без тулчейна TypeScript шим вызывает `install.sh`
(без Node — с `--ensure-node`) и перезапускается; без сети остаётся сигнал «harness inactive» или `unknown` проверок.

Привязка событий: `settings.json` в корне — user-level (на него ведёт симлинк `~/.claude/settings.json`), `.claude/settings.json` —
репозитория (вход через `.claude/bin/hook`).

Барьер, который не отработал, не пропускает: Node ≥ 24 не найден или рантайм упал с кодом не 0/2 — на
`PreToolUse` шим отвечает `ask` там, где человек видит вопрос (`default`, `acceptEdits`, `plan`), и `deny` в
`auto`, `bypassPermissions`, `dontAsk`; режим берётся из payload. На остальных событиях без рантайма шим молчит
и один раз за сессию печатает `systemMessage`. `CLAUDE_HARNESS_UNKNOWN` перекрывает режим на сессию: `ask`,
`deny` или `note` — примечание в `additionalContext` вместо решения.

## Как устроено

| Путь | Роль |
|---|---|
| `bin/hook <event>` | единственная точка входа: пин Node (`$CLAUDE_HARNESS_NODE` → `harness.env` → старший v24+ из `~/.nvm/versions/node` и `~/.claude/env/node` → `node` ≥ 24 в PATH) и пин TypeScript (`CLAUDE_HARNESS_TS` — экспортируется; сгнивший пин откатывается на тулчейн по `TOOLCHAIN.lock`); конфиг площадки чекаута; `NODE_COMPILE_CACHE`; снятие `NODE_OPTIONS` проекта; префильтр `pre-bash` по `bin/prefilter.regex` над копией команды без кавычек и `\` (промах у агента, `agent_id` в payload, — не выход, а запуск Node только для наблюдения friction: вердикт, падение и отсутствие рантайма до инструмента не доходят); код рантайма на pre-событиях перехватывается — не 0/2 значит `ask`/`deny` по режиму |
| `bin/run <script.ts \| --flag …>` | тот же пин Node, что у `bin/hook` (общий `bin/node-pin.sh`), для скриптов харнесса и его тестов: `harness/bin/run scripts/due.ts --all` из любого cwd (`~/.claude/harness/bin/run …` — через симлинк); путь как есть или относительно `harness/`; первый аргумент с «-» уходит node как есть; без Node ≥ 24 — rc 69, отката на `node` из PATH нет |
| `src/main.ts` | роутер `route()`: payload → гейты события (каждый в try/catch → `unknown(<имя>)`) → самый строгий вердикт → `emit()` |
| `src/emit.ts` | контракт выхода: `deny` rc 2 + stderr · `ask` JSON `permissionDecision` · `context` `additionalContext` (на stop и agent-stop — `systemMessage` человеку: additionalContext и block там дают модели новый ход, и его ответ подменяет итог или отчёт субагента) · Stop `decision: block` · `unknown` → на pre `ask`/`deny` по режиму, на остальных `context` |
| `src/config.ts` | конфиг площадки: `CLAUDE_HARNESS_CONFIG` → `~/.claude/harness.config.json` → `harness.config.json` в корне чекаута; нечитаемый файл — `problem`, и защищающие гейты закрываются (`pre-push-guard` — `unknown`, `owner-actions` — `deny`) |
| `src/state.ts` | `$CLAUDE_STATE_DIR/harness.db` (`node:sqlite`, WAL, `busy_timeout` первым): `verified`, `findings`, `deliveries`, `jobs`, `claims`, `stop_blocks`, `agent_window`, `markers`, … |
| `src/sweep.ts` | сверка дерева на каждом пишущем событии: `git status -z -uall` по корням сессии, sha256, сдвиг HEAD, ярусы проверок, доставка находок по читателю: журнал корня `deliveries` и журнал каждого субагента `agent_deliveries`, субагенту — только файлы его окна (`src/window.ts`); доставка — один раз на содержимое: вернувшийся к сломанному виду файл сообщается снова |
| `src/checks/` | `syntax` (bash -n / node --check / py_compile / JSON), `project-check` (`.claude/check.sh <file>` проекта), `tsc-project` (воркер, только проектный `tsc`), структурные проверки, `contour-suite` (воркер: набор контура при правке `harness/**`, `hooks/**`, `settings.json`) |
| `src/jobs/worker.ts`, `src/jobs/hold.ts` | detached-воркер дорогих проверок; кто держит задачу (живой воркер, запускающийся, никто) решает `hold.ts`. Stop заводит воркеры, как post, и ждёт их в окне 150 с (`awaitJob`), сам не выполняет ничего: задачу, которую никто не держит (сирота, мёртвый pid), compare-and-set'ом отдаёт новому воркеру; окно кончилось раньше результата — Stop блокируется, прогон идёт дальше, и следующий Stop любой сессии ждёт тот же воркер. Воркер обновляет отметку (`started_at`) перед каждым файлом — TTL 15 мин ограничивает одну проверку — и не закрывает задачу, которую у него забрали; сверка не ставит второй раз файл, который держит чужая задача, а проверку, оставшуюся `unstarted`, ставит снова. Замок `contour-suite` — пустой каталог, pid держателя рядом в `<замок>.pid`, и верится только записи новее замка; вердикт по файлу, сменившемуся во время проверки, выбрасывается; недоступное хранилище на Stop — `block` |
| `src/gates/` | гейты по событиям; реестр `registry.ts`, порядок — `index.ts` |
| `src/parsers/` | оболочка по грамматике: `lexer.ts` (POSIX §2.3, кавычки §2.2, here-doc §2.7.4, расширения bash) → `parser.ts` (рекурсивный спуск по §2.10) → `ast.ts` (узлы, `print`) → `model.ts` (Stage/Model для гейтов и ShellParse по сегментам); `shell.ts`/`stages.ts` — фасады, `stage.ts` — типы стадии и разборы обёрток; `legacy.ts` + `stages.ts` walk — старый токенизатор под `CLAUDE_HARNESS_SHELL_PARSER=legacy` до прогона по транскриптам (`scripts/shell-replay.ts`); `sql.ts` — libpg_query 17 (WASM, `vendor/`, `VENDOR.lock`) |
| `src/journal.ts` | JSONL-журналы с белым списком полей на журнал (I3) |
| `src/platform.ts` | единственный модуль с платформой: `process.availableMemory`, `spawnTool` с allowlist |
| `test/` | `node --test`; `_env.ts` — песочницы (реальный `HOME`/`~/.claude` недостижимы); `bench/` (`HARNESS_BENCH=1`), `e2e/` (`HARNESS_E2E=1`, стоит токенов) |

События (`bin/hook <event>`): `pre-bash` `pre-agent` `pre-write` `post` `post-batch` `agent-start` `agent-stop` `stop`
`session-start` `session-end` `prompt` `precompact` `worktree-create` `worktree-remove` `contour-changed`.
Привязаны в обоих `settings.json` 11 — все, кроме `post-batch`, `worktree-create`, `worktree-remove`, `contour-changed`.

## Выключатели

Каждый гейт и проверка гасятся своим `CLAUDE_SKIP_*=1` (читается роутером до любой записи). Список руками
не поддерживается — он печатается из реестра:

```sh
cd ~/.claude/harness && bin/run -e '
  await import("./src/gates/index.ts");
  const { GATES } = await import("./src/gates/registry.ts");
  const { CHECKERS } = await import("./src/checks/registry.ts");
  for (const g of [...GATES, ...CHECKERS]) console.log(g.name, g.killSwitch);'
```

Общего выключателя нет намеренно (I4): выключают один барьер, а не весь контур.

## Реестр предохранителей

Полный состав гейтов и сверки глазами модели: что останавливает, что требует шага, что ждёт окна, что пишет молча. CLAUDE.md держит только принцип и ссылку сюда; сообщение каждого deny/ask/block начинается с имени гейта (`src/emit.ts`).

Система строится так, чтобы **не зависеть от того, какая модель подключена**: haiku/sonnet/opus/fable/codex/mythos проходят одну планку, сильная быстрее, слабая дольше и дороже — но не хуже. Проверка любого элемента: *если качество зависит от того, насколько умна модель, элемент спроектирован неверно.*

**Каждый отчёт агента заканчивается секцией `## Трение`**: с чем столкнулся · как обошёл · что осталось в коде (тест/констрейнт/хук — или честное «ничего»). Для воркфлоу требование в промпте проверяет гейт; у Agent/Task — нет.

Отчёт и транскрипт агента харнесс **не читает** — это приватный текст. **Уровень** и **след** — свойства диффа: их считает `harness/src/friction.ts` на `SubagentStart`/`SubagentStop` и пишет в `~/.claude/exec-telemetry/personal-friction.jsonl` (`scope`, `trace_kind`, `safeguard_sufficient`, `attribution`); путей и содержимого в событии нет (тест). Агенту засчитывается только то, что записали его собственные вызовы (`adapter: claude-friction-3`, с 29.09): Write/Edit/NotebookEdit — по пути из post, Bash — по снимкам до и после его вызова, за вычетом файлов, которые в это время записали Write/Edit корня или другого агента. Корневая сессия не отслеживается, её pre-bash и post Bash friction не трогает. Фоновый Bash агента закрывается на его стопе; вызов без post (отказ гейта, прерывание) файлов не даёт и называется `missing_reason: call_unclosed`. `attribution: agent`, при другом открытом агенте в том же корне — `agent_overlapping` (узел `INC-FRICTION-AGENT-WINDOW-PARENT-EDITS`). Окно, открытое до выката, считается прежним диффом дерева (`claude-friction-2`). Агент без старта с типом (возобновлённый) — общее окно корня, `window`. Без старта и без типа — внутренний агент Claude Code: `internal`, уровня нет. Нарратив трения — `narrative_friction_state: unavailable`.

**Уровень считает скрипт по диффу, не модель** (функция / модуль / домен: миграция, схема, контракт, >1 репо); повысить его модель не может — входа для этого нет. **Решение качественное ⟺ в диффе остался детерминированный след** — формулировка отчёта на оценку не влияет. Миграция засчитывается следом только с констрейнтом/индексом, не «новая колонка».

**Повтор весомее первого появления.** Машина его не считает: повтор устанавливается сверкой с графом (`graph/incidents/`, тот же `root_cause`) на `/friction-review`. Домен и повторы идут к владельцу, остальное копится молча; на доменной правке без следа харнесс молчит (`silent`), доставка к владельцу — только через разбор. Предохранители по силе: констрейнт/индекс → property-тест/ассерт → хук → правило в скиле → строка здесь; **доменный уровень закрывается только констрейнтом или ассертом** — хук держит процессный риск, а не данные, схему или контракт (решение 22.09, так считает и `friction.ts`).

**Контур — планировщик, а не конвейер** (аналогия с БД): глубина проверки выбирается по `ущерб × P(ошибки)`; дешёвый детерминированный префильтр отсекает кандидатов до вызова модели; самая дешёвая проверка — та, которой не потребовалось (есть констрейнт — рассуждать не о чем); контекст не влезает — резать на срезы и сливать наверху.

**Реестр предохранителей**: все события `settings.json` идут в `harness/bin/hook` → `harness/src` (реестр — `src/gates/index.ts`); bash-хуки в `hooks/` заморожены и не подключены. Все молчат при штатном исходе; каждый гасится своим `CLAUDE_SKIP_*=1` из окружения процесса, не из команды — кроме `resource-guard`, который принимает разовый обход префиксом команды `CLAUDE_SKIP_RESOURCE_GUARD=1`. На pre-событиях «не разобрано» (`unknown`) в режимах `auto`, `bypassPermissions`, `dontAsk` — deny, в `default`, `acceptEdits`, `plan` — ask: проба 22.09 показала, что в bypass ask пропускает команду без вопроса. Человек возвращает ask на сессию `CLAUDE_HARNESS_UNKNOWN=ask`. Знать состав дешевле, чем узнавать о `deny` в момент отказа.

⛔ *Останавливают* — `model-gate` (явная модель у Agent/Task) · `workflow-friction-gate` (хотя бы один статический `agent()` не требует «Трение» ни в промпте, ни в `schema.properties.friction`) · `commit-msg-guard` (AI-атрибуция в сообщении коммита) · `pre-push-guard` (push и MR в защищённую ветку площадки (`protectedBranches`) не с `release/*`|`hotfix/*`; серия с локальной обвязкой; H1 — миграция под чужим штампом; H2 — `release/N+1` при незамкнутом прошлом релизе; исключения из правила обвязки — только списком владельца `harness/owner/pre-push-exceptions.json`) · `owner-actions` (разрешающий список к корпоративному GitLab: тег — создание, перенос, удаление, публикация любым refspec, `update-ref`, `glab release`, API `repository/tags`; запись в защищённую ветку — прямой push, DWIM-имена, глобы, автомерж push-опцией; мерж MR и API-мерж с целью в защищённой ветке — цель спрашивается у GitLab; недоказуемое — неизвестный каталог, смена состояния раньше в той же команде, `xargs`, команда из переменной — deny) · `owner-files` (`harness/owner/` — решения владельца: запись агента через Write/Edit/NotebookEdit и bash, который называет путь и не читает его, — deny; чтение, diff и `git add` открыты) · `memory-frontmatter` (шапка ноты: frontmatter, `name` = имя файла, четыре типа; только путь `~/.claude/projects/*/memory/`) · `pg-session` (барьер к Postgres на состоянии соединения: GUC без `LOCAL`, роль/база-левел настройки, `options=-c`; SQL, спрятанный подстановкой, — deny) · `bash-writes` (файл, который команда пишет литеральным текстом, проходит гейты записи как Write) · `migration-name` (имя миграции не `<снятый timestamp>-<kebab>.ts` либо класс/`name` несут другой timestamp) · `data-boundary` (pre-bash: строки бизнес-таблиц с прода, выборка больше 1000 строк из нелокального контура, печать секрета; конфигурация и агрегаты проходят; SQL через MCP гейт не видит) · `shell-grammar` (команда вне грамматики оболочки, а в неразобранном остатке — слово любого pre-bash гейта: unknown; держит I1 для всех гейтов разом).

⚠️ *Требуют следующего шага* — сверка дерева `sweep` на post/post-batch (не на agent-stop: вывод SubagentStop — новый ход субагента, его ответ подменяет отчёт; учёт доставки по читателю — находка ждёт post или Stop корня, субагент слышит только о файлах своего окна и никогда «проверок в фоне»): `syntax`, `project-check` (`.claude/check.sh` проекта), `tsc-project`, `comment-bloat` (блок >5 строк вне шапки, история правки, больше одного комментария в теле функции, комментарий в параметрах и в SQL-литерале), `comment-language` (язык комментариев по `git config harness.comment-language`), `tripwire` (publish/emit/after-commit/one-shot → `code-delivery-audit`), `contour-suite`. Находка приходит в сессию один раз; `sweep-stop` блокирует Stop только на находке, впервые доставленной на Stop (фоновые `tsc-project`/`contour-suite`), или на недренированной очереди — находки sync-яруса, показанные после правки, Stop не держат · `memory-index` (Stop, совет: нота без строки в `MEMORY.md`) · `memory-guard` (свободная память ниже 200 МБ, рост swap >200 МБ). На Stop будит модель только `block`; заметки (`memory-index`, `memory-guard`, `git-freshness`, повтор подписи `sweep-stop`, `unknown`) идут владельцу `systemMessage`'ем — `additionalContext` на Stop тоже дал бы модели лишний ход (решение 24.09).

⏳ *Ждут окна* — `resource-guard` (тяжёлая команда — jest, тест/билд-скрипты npm/yarn/pnpm/bun, gradle, xcodebuild, docker build — при <2000 МБ или load >2.0/ядро ждёт до 240 с шагом 15).

🔇 *Пишут молча* — `git-freshness` (сдвиг HEAD в вольте и четырёх репах WMS с ТСД, fetch не чаще 600 с; после fetch `source` перематывает локальные ветки `freshness.sync.branches` локальным `git fetch . source/<b>:<b>` без `+` — только fast-forward, не занятые воркtree (корневой чекаут, rebase и bisect — тоже заняты) отбивает сам git; впереди/разошлась/занята/отказ — не трогает, заметка владельцу на Stop раз на состояние) · `friction` → `personal-friction.jsonl` · `telemetry` → `personal.jsonl`/`corp.jsonl` · `capture-commits` (без темы/email, только репо cwd) · `precompact-snapshot` · `work-docs-reminder` · `session-start` (печатает назревшие ревизии в каждой сессии: расписание мозга из `harness.db`, туда же пишет `due.ts --done <id>`; воркtree мозга считается мозгом) · `tracker-inbox` (старт сессии: неразобранные `@agent` локального трекера — номера карточек; трекер не ответил — так и сказано; молчит там, где трекер не установлен) · `friction-prefilter` (узлы графа старше 14 дней) · `toolchain-signal`.

Проверки контура — `harness/test/**/*.test.ts` на тулчейне `harness/TOOLCHAIN.lock` (Node из `~/.claude/env/harness.env`); при правке `harness/**`, `hooks/**`, `settings.json` их прогоняет `contour-suite` (кеш по поколению, прогон из нуля тестов — fail). `hooks/spec/*.test.sh` заморожены с 16.09. Префильтр шима (`harness/bin/prefilter.regex`) отсекает команду до Node — новое слово гейта обязано попасть в `prefilters.ts`, иначе гейт недостижим. Мета-тест держит равенство regex ↔ `prefilters.ts` и перечисленные формы, а не полноту: каждая deny-форма `owner-actions` прогоняется через тот же grep, что и шим. Открытая граница: `pg-session` по построению пропускает чистый `SELECT`, поэтому поход в базу через `kubectl exec` он не отбивает (память `no-prod-db-access`).

Граница `owner-actions`. Тег, прямой push в защищённую ветку (`protectedBranches`) и мерж MR с целью в ней держит гейт `owner-actions` — разрешающим списком: push в корпоративный GitLab проходит, только если каждый refspec — существующая локальная незащищённая ветка; glab — только известные подкоманды; всё недоказуемое — deny (хуковый ask в auto и bypass человеку не показывается). Клиент мимо git/glab/curl-к-`/api/v4/` гейт не видит: второй барьер — защищённые теги `v*` и защищённые ветки в самом GitLab, их выставляет владелец.

## Границы — что сверка не видит

Файлы под `.gitignore` (`.env`, `dist/`); деревья вне git (scratchpad); правки внутри контейнера/пода и в базе;
изменения после Stop до следующей сессии; деревья с числом изменённых файлов > 200 (сообщается `truncated`);
обфускация shell глубже одного уровня `sh -c`/`eval`, `base64 -d | sh`, команда из переменной — даёт `unknown`, не pass.
Команда, которую грамматика оболочки не дочитала, со словом любого pre-bash гейта в недочитанном хвосте — тоже
`unknown` (`shell-grammar`).
Here-doc в эти границы НЕ входит: тело `<<EOF` разбирается и судится (`git commit -F -`, `psql <<SQL`), а
`unknown` остаётся только там, где текст и правда неизвестен — подстановка в теле при голом ограничителе,
ограничитель без закрытия, here-string `<<<`, stdin из трубы.
Функция-обёртка `run() { psql … "$@"; }` с литеральными вызовами в той же оболочке — тоже не граница: pg-session
раскрывает её по каждому вызову и судит argv psql, который получится (плоское тело, безусловный `shift`, `"$@"`/`"$1"`
целым словом в кавычках). Условный `shift`, `set --`, `eval`, `"$*"`, `${@:2}`, вызов с подстановкой, из другой оболочки
или функция без вызова оставляют SQL скрытым — deny с причиной, чего не хватило.
Строка-команда обёртки — `docker exec … sh -c '…'`, `su -c '…'`, `ssh host '…'`, `watch '…'`, `find -exec sh -c '…'` —
разбирается как уровень +1, и stdin обёртки (here-doc, `<`, труба) доходит до команд её тела. Файл, который команда
пишет литеральным текстом (here-doc, echo, printf, tee — прямо или через трубу), проходит гейты записи так же, как
Write (`bash-writes`); содержимое, которого в команде нет — cp, sed -i, curl -o, скрипт, подстановка — не судится.
Закоммиченный сломанный файл сообщается один раз при сдвиге HEAD, дальше это забота тестов проекта.

## Известные дефекты

Критика 25.09 с репродьюсерами; исправлены «сломал → починил → снова сломал» и проход Stop при залоченном
хранилище. Остальное воспроизведено и открыто:

- **высокий** — вердикт воркера по закоммиченному файлу теряется или уходит не той сессии: курсор `last_head` —
  один на репозиторий, его забирает первая сверка, увидевшая сдвиг HEAD (правка и коммит в одном вызове, коммит
  во время фоновой проверки, чужая сессия в том же репозитории);
- **высокий на больших проектах** — дренаж Stop может не завершиться: `tsc-project` гоняет полный `tsc -p` на
  каждый файл задания, а Stop, убитый таймаутом, оставляет задание `running` под мёртвым pid и следующий
  начинает его заново;
- **средний** — Stop одной сессии блокируется фоновыми проверками другой и не ждёт их в своём бюджете дренажа;
  `stop_hook_active` не читается;
- **средний** — телеметрия разбирает транскрипт внутри транзакции хранилища: лок дольше `busy_timeout` делает
  Stop `block` (не проход, но лишний ход модели);
- **средний** — дубли строк в журнале коммитов: индекс и дозапись идут в одной транзакции до COMMIT;
- **средний** — восстановление битого хранилища переименовывает его под живым соединением (`-wal`/`-shm` не
  переезжают): свежее состояние теряется, находка доставляется повторно;
- **средний** — `git-freshness` ведёт одну строку на репозиторий, а не на сессию: заметку о чужом коммите
  получает одна сессия, а печать на Stop гасит её для всех;
- **низкий** — окно агента без stop остаётся открытым навсегда (`friction`); откат часов на час останавливает
  fetch в `git-freshness` на 1 ч 10 мин.
- **средний** — перемотка `git-freshness` (`git fetch . source/<b>:<b>`) видит воркtree только в момент записи:
  `checkout` этой ветки, который уже прочитал её и ещё распаковывает дерево, получит сдвинутую ветку под старым
  деревом (`git status` покажет изменения ремоута застейдженным откатом). Окно — длительность того checkout.
  Не-fast-forward, ветку под rebase/bisect и коммит в ветку между чтением и записью отбивает сам git.

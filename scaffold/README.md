# Генераторы: как в контуре рождается новый элемент

`brain new <вид> <имя>` создаёт элемент в той форме, которую требуют мета-тесты, и подключает его туда, где его
ищут роутер, шим и карта скиллов. Сгенерированное правило молчит на всём, кроме своей цели, а на цели отвечает
`unknown`, пока правило не написано: генератор никогда не выдаёт тихий pass.

| Вид | Что создаёт | Куда подключает |
|---|---|---|
| `skill` | `skills/<имя>/SKILL.md`, `evals/evals.json` | строка в `skills/README.md`, раздел «Свои» |
| `gate` | `harness/src/gates/<имя>.ts`, тест с kill-switch | `gates/index.ts` (до `bash-writes`), слово `--trigger` в `prefilters.ts` и `bin/prefilter.regex` |
| `checker` | `harness/src/checks/<имя>.ts`, тест | `checks/index.ts` |
| `agent` | `agents/<имя>.md` без модели (наследует корень) | — |
| `runtime` | `runtimes/<имя>.ts` по контракту `runtimes/core.ts`, тест N/A-таблицы | шаги для `bin/brain` печатаются |
| `spec` | `specs/SPEC_<ИМЯ>.md` | — |
| `preset` | `presets/<имя>/` — README, фрагмент конфига, `bin/`, `skills/` | — |

```sh
brain new list
brain new gate helm-guard --trigger helm --purpose "helm upgrade только в свой namespace"
brain new skill release-notes --description "релиз уходит людям: что изменилось и для кого"
brain new spec helm-guard
brain new gate x --dry-run          # показать, что будет записано, ничего не трогая
```

## Порядок, которым собран сам контур

Каждый гейт и проверка ядра прошли один и тот же путь. Генератор — первый шаг этого пути, не замена ему.

1. **Спека** (`brain new spec`): проблема фактами (файл:строка, счёт по журналам, воспроизведение), цели, не-цели,
   инварианты, таблица «инвариант → тест». Скилл `code-spec-and-verify`.
2. **Критик спеки** — субагент `spec-critic` по редакции. Дыры принимаются по коду, не по мнению; редакций
   столько, сколько нужно, чтобы критик перестал находить.
3. **Исполнитель** — тест красный до правки, правило в `decide()`/`judge()`. Только парсеры: команда —
   `parsers/shell.ts`, SQL — `parsers/sql.ts` (libpg_query), TS — compiler API проекта. Regex — только по строкам
   без грамматики (имя файла, ветки, сообщение коммита), и это названо в шапке модуля. Конвенции —
   `harness/PORTING.md`.
4. **Аудитор** — субагент `race-auditor` по диффу: гонки, обходы, «недоказуемое молча проходит».
5. **Отчёт**, если результат уходит людям, — скилл `verification-report`. Каждый отчёт агента заканчивается
   секцией `## Трение`.

Сила предохранителя: констрейнт/индекс → property-тест/ассерт → гейт или проверка → правило в скилле → строка в
`CLAUDE.md`. Генератор скилла — самый слабый уровень; если нарушение ловится машиной, следующий шаг — `gate`/`checker`.

## Публичный слой из приватного мозга

Сам CH-T собран тем же способом, каким собирается любой публичный слой из приватного рабочего репозитория:
`harness/scripts/export.ts`. Приватный манифест (вне git) называет, что выгружать (`include`/`exclude`),
публичные шаблоны и список запретов (`deny` — имена работодателя, хостов, людей, веток); к запретам автоматически
добавляются значения `harness.config.json`. Любое совпадение роняет выгрузку до записи первого байта.

```sh
cd harness && ~/.claude/harness/bin/run scripts/export.ts --out /tmp/public --manifest ~/private/export.json --test
```

Свои правки ядра держи конфигом, а не кодом: всё, что принадлежит площадке (ветки, хосты, таблицы, каналы прода),
живёт в `harness.config.json` и пресетах — тогда ядро переносится между мозгом и этим репозиторием без правок.

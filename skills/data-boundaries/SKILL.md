# Границы данных

Три правила, из которых выводится всё остальное.

**Прод показывает устройство, а не содержимое.** Конфигурация по слоям, схема, настройки,
счётчики, планы запросов — да. Строки бизнес-таблиц — нет, никогда, включая «одну строчку
для примера». Причина не в вероятности утечки, а в том, что решения о продукте принимаются
по конфигурации и агрегатам; строка нужна тому, кто хочет посмотреть на конкретного
человека, и такой задачи у нас не бывает.

**Наполнители мы делаем сами.** Форму берём с тестовых сред: какие поля, какая длина,
какие значения допустимы, какие связи обязательны. Значения генерируем. Скопированная
«живая» строка выглядит удобнее сгенерированной ровно до момента, когда она уезжает в git,
в отчёт или в тикет.

**Объём сам по себе является нарушением.** Выборка, которую не читают глазами, перестала
быть проверкой факта и стала срезом среды. Порог грубый и намеренно низкий: тысяча строк.

## Порядок

Анкету не заполняют по памяти — её печатает скрипт, потому что ответы «чувствительны ли эти
данные» и «раскрывают ли они человека» суть свойства класса, а не суждение в моменте:

```bash
~/.claude/harness/bin/run scripts/data-answers.ts --classify "<команда или описание операции>"
~/.claude/harness/bin/run scripts/data-answers.ts --env dev --kind rows --dest external
```

Вердикт бывает четырёх видов, и каждый означает конкретное следующее действие.

| Вердикт | Что делать |
|---|---|
| `ALLOW` | выполнять как есть |
| `ANONYMIZE` | выполнить внутри среды, наружу отдать обезличенное (см. ниже) |
| `SYNTHESIZE` | не брать данные вообще, сгенерировать |
| `DENY` | не выполнять; если факт всё равно нужен — переформулировать вопрос в агрегат |

Гейт `data-boundary` харнесса блокирует три класса независимо от анкеты: прод-строки, выгрузку
из непокального контура и печать секрета. Он срабатывает на команде, а не на намерении,
поэтому спорить с ним бесполезно — если он сработал, вопрос задан неправильно. То, что он
доказать не может (SQL не разобран, выборка без LIMIT вне локального контура, GROUP BY по
колонке бизнес-таблицы на проде), он не пропускает молча, а спрашивает подтверждение.

## Переформулировка вместо отказа

Отказ гейта почти всегда означает, что вопрос можно задать иначе и получить тот же ответ.

| Хотелось | Спросить вместо этого |
|---|---|
| посмотреть строки заказов на проде | `count(*) FILTER (WHERE status = …)` по нужным статусам одним запросом |
| понять форму записи | схему таблицы из `information_schema`, а не саму запись |
| «а есть ли там вообще данные» | `count(*)`, `min/max` по ключу, `pg_stat_user_tables.n_live_tup` |
| воспроизвести дефект на реальных данных | воспроизвести на сгенерированных с той же формой |
| приложить пример к отчёту | сгенерированный пример той же структуры, помеченный как синтетический |
| выгрузить срез для анализа | посчитать нужный агрегат прямо в базе и забрать числа |

## Как генерировать наполнители

Форма снимается с тестовой среды один раз и записывается как контракт: перечень полей,
типы, обязательность, диапазоны, связи. Дальше генератор делает данные по контракту.

Это должен быть **скрипт-сид, а не разовая вставка руками**: идемпотентный (`ON CONFLICT`),
параметризованный количеством, кладущий данные в понятные диапазоны. Такой сид переживает
пересоздание стенда и читается как документация формы. Значения делаем заведомо
искусственными: `FLOWCHK-SKU-1`, `+996700000001`, `test-«домен».invalid` — чтобы ни один
человек, глядя на них, не принял их за настоящие и не пошёл по ним звонить.

Персональные поля генерируем всегда, даже на локальном стенде. Скопированный однажды
телефон живёт в фикстурах годами.

## Обезличивание

Обезличенное — это не «убрал фамилию». Уникальные идентификаторы и редкие сочетания
опознают человека не хуже имени. Обезличенная форма выглядит так: идентификаторы заменены
на стабильные суррогаты, точные времена огрублены до часа или дня, редкие значения свёрнуты
в категорию, а наружу уходит агрегат, где на каждую строку приходится несколько объектов.

## Автотесты

Автотесты гоняем на дев-среде на её данных: там они настоящие по форме и не персональные по
происхождению. Конфигурация прогона записывается, чтобы результат можно было повторить.
Наружу из прогона уходят метрики и вердикты, не выборки. Наблюдение с дев-среды становится
фактом о продукте по обычным правилам `local-stand-findings`, границы данных этого не меняют.

## Секреты

Секрет не печатаем и не пишем в файл репозитория. Проверять наличие — `test -s`, состав
k8s-секрета — по именам ключей без расшифровки. Значение передаётся сразу потребителю, в той
же команде, без промежуточной печати: `kubectl create secret … --from-literal=<ключ>="$(…)"`.
Токен, уехавший в транскрипт, считается скомпрометированным и подлежит ротации — это дешевле,
чем спор о том, кто его увидит.

## Смежное

`local-stand-findings` — можно ли считать наблюдение фактом. `metrics-verify` — честна ли
цифра. `db-performance` — быстрый ли запрос. Границы данных отвечают на другой вопрос:
имею ли я право это видеть и в каком виде это можно вынести наружу.

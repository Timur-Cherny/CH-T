# Граф знаний по архитектуре

Граф знаний — не картинка и не список ссылок. Это **типизированные узлы и
типизированные направленные связи** плюс правило, по которому каждый узел
проверяется на истинность. Без последнего это просто ещё один документ, который
устаревает молча.

## 1. Онтология прежде графа

Сначала фиксируются **типы узлов** и **типы связей**, потом наполняется. Иначе
каждый следующий документ вводит свои названия для того же и граф перестаёт
соединяться.

Наши типы узлов:

| тип | что это | пример |
|---|---|---|
| `сервис` | развёртываемая единица | движок, коннектор, веб-фронт, мобильный клиент |
| `сущность` | таблица или доменный объект | `orders`, `moves`, `units` |
| `правило` | конфигурация, задающая поведение | опция стадии, тип операции |
| `механизм` | именованный кусок поведения | резерв, каскад тары, менеджер статусов |
| `контракт` | граница между сервисами | Kafka-топик, REST-эндпоинт, DTO |
| `дефект` | известная поломка | запись бэклога, задача трекера |

Типы связей — направленные, глагол в настоящем времени:

`читает` · `пишет` · `вызывает` · `порождает` · `ограничивает` ·
`интерпретирует` · `противоречит` · `ломает`

Связь без типа («связано с») бесполезна: она не даёт вывести следствие.

## 2. Один уровень абстракции на одну картину

Правило C4: система → контейнеры → компоненты → код. **Не смешивать уровни в
одной схеме.** Картина, где рядом стоят «коннектор» и «поле
`unitParentId`», нечитаема: у читателя нет масштаба.

Для каждой картины сначала называется уровень, потом рисуется. Переход между
уровнями — отдельная картина со ссылкой.

## 3. Источник истины у каждого узла

Каждый узел несёт, **чем он проверяется**:

- `сервис`, `механизм`, `контракт` → `file:line` в репозитории;
- `правило` → SQL-запрос к конфигурации;
- `сущность` → схема таблицы;
- `дефект` → воспроизведение или запись бэклога.

Узел без источника истины — гипотеза, и помечается как гипотеза. В графе это
допустимо, но должно быть видно с одного взгляда.

## 4. Метка проверки и устаревание

Граф устаревает молча — это его главная болезнь. Поэтому:

- каждая ветка несёт **дату и коммит** проверки;
- при расхождении графа с кодом правится граф, а не наоборот;
- проверка идёт **против источника истины**, а не против другого документа:
  документ, проверенный по документу, воспроизводит его ошибку.

Практическое следствие: перед тем как опереться на узел в решении, проверь его
метку. Метка старше релиза — перепроверь, прежде чем использовать.

## 5. Что граф обязан показывать, кроме связей

Ценность графа не в перечислении, а в трёх вещах, которых нет в отдельных
документах:

1. **Кто интерпретирует правило.** Одна конфигурация может читаться несколькими
   исполнителями по-разному. Граф показывает всех читателей узла разом — это
   единственный способ увидеть, что клиенты разошлись.
2. **Противоречия.** Связь `противоречит` — полноценный тип. Две опции,
   разрешающие и запрещающие одно и то же, обязаны быть соединены.
3. **Что нельзя дописать задним числом.** Данные, которые не собираются
   сейчас, потом не восстановить. Отдельный список, а не примечание.

## 6. Как строить

1. **Уровень.** Один на картину.
2. **Узлы с типами.** Только то, что нужно для вопроса, ради которого граф.
3. **Связи с глаголами.** Направление обязательно.
4. **Источник истины** к каждому узлу.
5. **Проверка на противоречия**: пройти по парам узлов, ограничивающих одно и
   то же, и явно назвать несогласованные.
6. **Метка** даты и коммита.

## Приёмка графа

- [ ] один уровень абстракции;
- [ ] у каждого узла тип из онтологии, у каждой связи — глагол и направление;
- [ ] у каждого узла источник истины либо пометка «гипотеза»;
- [ ] показано, кто интерпретирует каждое правило;
- [ ] противоречия названы связью, а не спрятаны в текст;
- [ ] есть дата и коммит проверки;
- [ ] правила скилла `project-documentation` соблюдены — граф это документ.

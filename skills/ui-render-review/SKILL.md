# CSS/DOM-render review — фронтенд (стадийные экраны)

Цель: найти ВСЕ механизмы, из-за которых заливки блоков «прыгают» и появляются секундные артефакты при смене статусов и на ошибках стадий. Ревью, не фикс: каждая находка = механизм + экран + file:line + направление фикса.

## Известные проектные ловушки (проверять В ПЕРВУЮ очередь)

1. **Глобальный reset в `src/globals.css`**: `div.MuiBox-root .MuiBox-root:not([data-stage-scope] *):not(.badge) { background: transparent !important }`. Уже бил один раз (прозрачные фильтр-чипы, фикс `:not(.badge)`). Классы механизма:
   - элемент на кадр рендерится ДО появления `data-stage-scope`-предка или нужного класса → reset применяется → заливка мигает;
   - порталы/модалки MUI рендерятся ВНЕ `[data-stage-scope]`-поддерева → reset бьёт по ним постоянно или на кадр;
   - любой новый цветной Box без `.badge`/`data-stage-scope` тихо теряет фон.
2. **styled-components v6 + MUI вперемешку**: инъекция `<style>` асинхронная; при ремаунте больших поддеревьев возможен кадр без правил (FOUC) — фон падает в unstyled/reset-состояние.
3. **Ремаунт вместо обновления** — подтверждённый в проекте паттерн (details-страница жила в цикле Loading↔remount, чинилось page-owned fetch'ем). Искать: условный рендер, меняющий ЦЕЛОЕ поддерево (`isLoading ? <Loading/> : <Content/>`, `error ? <Overlay/> : ...`), смену `key`, размонтирование хедеров/карточек при рефетче.
4. **react-query v3**: `refetchInterval`-поллинг (10s на деталях) + `retry` → каждые N секунд транзиентные error/loading состояния → если UI реагирует сменой поддерева, а не точечным стилем — артефакт раз в цикл поллинга.

## Процедура

### A. Статический свип CSS
- Все `!important` и глобальные селекторы (globals.css, createGlobalStyle, GlobalStyles MUI) — против каких компонент стадийных экранов они конкурируют.
- `getStatusColor` / статусные заливки: где цвет приходит из props/тем vs из класса; есть ли переходные состояния, где статус ещё undefined → какой фон рендерится.
- `transition`/`animation` на `background-color`: где смена статуса анимируется, а где скачет; где transition случайно анимирует ПОЯВЛЕНИЕ reset-фона.
- Порталы (Dialog/Popover/Snackbar/Tooltip) vs `[data-stage-scope]`: что из стадийного UI живёт в портале и попадает под reset.

### B. Свип рендер-путей (React)
- В `src/features/actions/stages/**` и `src/features/actions/picking/**`: найти все места, где смена статуса/ошибка приводит к unmount+mount вместо обновления пропсов. Маркеры: тернарники целых поддеревьев, изменяемые key, компоненты, объявленные ВНУТРИ рендера (новая identity каждый рендер → ремаунт).
- Ошибочные состояния: `big-error-overlay`, `load-error`, `scan-error`, ErrorScreen, тосты — что они делают с СОСЕДНИМИ блоками (перекрывают/вытесняют/пересоздают). Layout shift: появление баннера ошибки двигает контент?
- Optimistic/транзиентные статусы: между PATCH мува и рефетчем — какой статус показан, каким фоном.

### C. Runtime-подтверждение (если доступен браузер)
- Воспроизвести: экран стадии → закрыть мув → в окно рефетча наблюдать фоны (запись/скриншоты по кадрам). Спровоцировать ошибку стадии (скан невалидного ШК) и смотреть артефакты.
- В DevTools: Rendering → Paint flashing; Elements → зафиксировать, какие правила применяются в момент мигания (кто перебивает кого).

## Формат находок

По каждой: `[severity] Механизм — экран/компонент — file:line — чем проявляется (какой артефакт) — направление фикса (НЕ патчить)`. Severity: high = видимый глюк в основном флоу; med = проявляется на ошибках/медленной сети; low = теоретический/косметика. В конце: сводная таблица «механизм → сколько мест» и рекомендация, что чинить первым.

Отдельным разделом: **проверка гипотезы про globals.css reset** — подтверждена/опровергнута, с доказательством (список элементов под ударом).

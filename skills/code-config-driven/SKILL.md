# Архитектура, где поведение задают данные

Такая система — не «код с настройками». Это **Adaptive Object-Model** (Yoder & Johnson,
OOPSLA 2001): бизнес-правила лежат снаружи кода, а код — интерпретатор чужой
модели. Отсюда всё остальное в этом файле.

Соответствие один в один:

| паттерн AOM | пример (сервис заказов) |
|---|---|
| TypeObject | `process_types` → `process_type_stages` (тип) vs `orders` / `tasks` (экземпляр) |
| Property | `process_type_stage_options` — имя/значение в jsonb |
| RuleObject | `scanningPriority`, `carrierInteraction`, `taskStatusChangeMethod`, `allowPartialFinish` |
| Interpreter | движок, читающий опции в рантайме |
| снимок типа | `tasks.task_options` — копия опций на момент создания заказа |

## Главное следствие: код не является источником истины о поведении

В обычной системе «что делает программа» отвечает код. Здесь код отвечает только
«что программа **может** делать»; что она делает — отвечают данные.

Поэтому **вывод о поведении, сделанный по одному чтению кода, — гипотеза.**
Проверяется запросом к конфигурации, а не рассуждением.

```sql
SELECT pts.type, opt.code, opt.value::text
FROM process_types pt
JOIN process_type_stages pts ON pts.process_type_id = pt.id
JOIN process_type_stage_options opt ON opt.stage_id = pts.id
WHERE pt.name = '<тип операции>'
ORDER BY pts.sorting, opt.code;
```

## Правила работы

### 1. Перед правкой — прочитать конфигурацию всех типов операций, а не одного

Ветка `if (options.X === 'allow')` живёт по-разному на каждом типе операции.
Правка, проверенная на одном, ломает другой молча. Смотреть ВСЕ значения опции,
которую трогаешь, включая «опция не задана» — это отдельное, самое частое
значение.

### 2. «Опция не задана» — полноценная ветка, а не край

Отсутствие опции обычно означает легаси-поведение, и оно не совпадает ни с
`allow`, ни с `not_allow`. В спеке и в тестах эта ветка обязана быть named.

### 3. Конфигурация говорит — интерфейс обязан отвечать

Если данные объявляют режим, UI обязан дать пользователю способ его отработать.
Стадия с `taskStatusChangeMethod: manual` без кнопки завершения — не «мелочь
UX», а **нарушение архитектуры**: система заявила, что решает человек, и не дала
человеку органа управления.

Проверять симметрично: для каждого значения опции — какой контрол его
обслуживает. Пустая клетка в этой таблице и есть дефект.

### 4. Правило живёт в одном месте — на сервере

Клиент, повторяющий серверное правило, расходится с ним при первом же изменении
данных, и расходится **молча**: кнопка исчезает, список пустеет, ошибки нет.
Если движок уже считает флаг — читать флаг, а не выводить его заново.

Симптом для поиска: константа-список кодов/статусов/причин в клиенте, повторяющая
доменное правило.

### 5. Тесты обязаны параметризоваться конфигурацией, а не примером

Тест на одном наборе опций проверяет одну клетку матрицы. В AOM-системе матрица и
есть предмет проверки. Минимум — таблица «значение опции → ожидаемое поведение»,
включая незаданное.

Первоисточник признаёт это прямо: инструменты тестирования и поддержки для AOM
**недоразвиты**. Значит их строим мы, а не ждём от фреймворка.

### 6. Снимок опций ≠ текущие опции

`tasks.task_options` — копия на момент создания. Правка типа операции **не
действует** на уже созданные заказы. Любое «я поменял настройку, а не работает»
проверяется сравнением снимка с текущим типом, а не перечитыванием кода.

### 7. Миграция данных — часть правки поведения

Изменение поведения в такой системе часто выглядит как правка строки в БД. Из
этого следует: миграция идемпотентна, имеет рабочий `down()`, и — если конфигурацию
кеширует воркер — выкат включает рестарт. Без рестарта миграция «не применилась»
при формально успешном деплое.

## Обратная сторона: часы конфигурационной сложности

Mike Hadlow, Configuration Complexity Clock: система идёт по кругу от хардкода
через файлы настроек и иерархические схемы к движку правил и собственному DSL — и
возвращается к хардкоду, но уже на **худшем языке, без отладчика и без тестов**.

Вывод оттуда, который стоит держать при добавлении каждой новой опции:

> «На определённом уровне сложности хардкод может оказаться наименьшим злом».

Практический критерий, когда НЕ выносить в данные:

- значение меняется реже, чем выходит релиз, — это константа, а не опция;
- ветку по опции невозможно объяснить пользователю системы — это не бизнес-правило,
  а деталь реализации;
- новая опция осмысленна только в паре с другой — значит моделируется не то;
- проверить комбинацию можно только руками на стенде — матрица уже переросла
  инструменты.

## Что писать в ADR по такой системе

Обязательные разделы, без которых ADR неполон:

1. **Матрица опций** — какие значения затрагивает решение и что делает каждое,
   включая незаданное.
2. **Кто интерпретатор** — сервер, клиент или оба. Если оба — почему это не
   разъедется.
3. **Судьба снимка** — что происходит с уже созданными заказами.
4. **Способ выката** — миграция, рестарт кеширующих воркеров, порядок с
   потребителями контракта.
5. **Что проверяемо детерминированно** — какой инвариант закрывается констрейнтом
   или тестом, а не договорённостью.

## Приёмка

Правка в AOM-системе принята, когда:

- прочитаны все значения затронутой опции по всем типам операций;
- ветка «опция не задана» названа явно;
- для каждого значения, требующего действия человека, в UI есть орган управления;
- правило не продублировано на клиенте;
- тест параметризован конфигурацией и краснеет без правки.

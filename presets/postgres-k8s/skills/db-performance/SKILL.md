# Работа с базой: устанавливать, а не гадать

Правило нулевое: **чтение кода даёт гипотезу, факт даёт запрос к базе.** Оптимизация по интуиции обходится дороже, чем отсутствие оптимизации: неверная догадка стоит дня работы исполнителя и оставляет настоящую причину нетронутой.

Порядок всегда один: **замерить → прочитать план → назвать причину → починить → замерить снова.** Пропуск любого шага возвращает к гаданию.

## 1. Прежде чем верить `pg_stat_statements`

Счётчики кумулятивны с момента сброса. Суммарные `calls` и `mean_exec_time` описывают **всё окно сразу**, а не сегодняшний день.

```sql
SELECT stats_reset, now() - stats_reset AS window FROM pg_stat_statements_info;
```

Окно в полгода означает, что запись могла целиком относиться к периоду **до** выката, который эту проблему уже закрыл. Реальный случай: запись с `mean 1505 мс` по списку `moves` описывала период до фикса; после фикса тот же запрос давал 0–1 мс, и вся аргументация «прод тормозит вот здесь» была неверна.

В PostgreSQL 18 есть `stats_since` у каждой записи — момент, **с которого копится запись**. Он отвечает на вопрос «появилась ли запись после выката», но **не** отвечает на вопрос «когда её выполняли в последний раз». Различать обязательно.

```sql
SELECT calls, round(mean_exec_time) mean_ms, round(max_exec_time) max_ms, stats_since,
       left(regexp_replace(query,'\s+',' ','g'),100) q
FROM pg_stat_statements
WHERE stats_since > '<дата последнего выката>' AND calls > 2 AND mean_exec_time > 300
  AND query NOT LIKE 'EXPLAIN%'
ORDER BY mean_exec_time DESC LIMIT 15;
```

Две дисциплины из этого:

- **сравнивать `max_exec_time` с клиентским таймаутом.** Максимум выше таймаута — это и есть отменённые запросы. Так связывается «падает в браузере» с конкретной строкой SQL;
- **исключать собственные `EXPLAIN`.** Свой прогон попадает в статистику отдельной записью и потом выглядит как прод-нагрузка. Помнить об этом и говорить вслух, если цифра приводится другим.

Гигиена: **сбрасывать счётчики после каждого выката**, чтобы окно совпадало с версией кода. `SELECT pg_stat_statements_reset();` — запись, на проде выполняет человек.

## 2. Как читать `EXPLAIN`

`EXPLAIN` показывает план. `EXPLAIN ANALYZE` **выполняет запрос** — на `UPDATE`/`DELETE` только внутри транзакции с откатом.

```sql
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF) <запрос>;
```

`BUFFERS` обязателен. Миллисекунды скачут от прогретости кэша и конкуренции; **число страниц — честная единица**, оно почти не зависит от того, в какой момент снят замер. 70 774 буфера против 287 — это разница, которую не спишешь на нагрузку.

Что искать, в порядке убывания частоты:

| признак в плане | что значит |
|---|---|
| `Seq Scan` по крупной таблице при селективном фильтре | индекс отсутствует, непригоден или не выбран |
| `rows=1` в оценке при `actual rows=52` и выше | статистика врёт, план построен под неверный объём |
| селективный узел **наверху** плана | фильтр применяется последним, до него джойнится всё |
| `loops=N` с большим N у дорогого узла | вложенный цикл по большому внешнему набору |
| `Batches: N` при N > 1 в Hash/Sort | не хватило `work_mem`, ушло на диск |
| `Rows Removed by Filter` порядка размера таблицы | таблица прочитана целиком ради нескольких строк |

План читается **снизу вверх**: нижние узлы выполняются первыми. Селективный индексный поиск, оказавшийся на вершине, — типовой признак того, что планировщик не смог поставить фильтр вперёд.

## 3. Выбор индекса — по свойству запроса, а не по привычке

| ситуация | индекс |
|---|---|
| равенство и диапазон по скалярной колонке, сортировка | **btree** — умолчание, покрывает ≥90 % случаев |
| запрос **всегда** несёт один и тот же предикат (`deleted_at IS NULL`, `status='active'`) | **partial** — меньше, дешевле в записи; см. ловушку ниже |
| несколько колонок в одном фильтре | **составной**: сначала колонки на равенство, потом на диапазон и сортировку |
| выборка читает 1–2 колонки сверх ключа | **covering** через `INCLUDE` — даёт Index Only Scan |
| поиск внутри `jsonb`, массива, полнотекст | **GIN** |
| диапазоны, геометрия, `&&` по интервалам | **GiST** |
| очень большая таблица, физический порядок совпадает с логическим (append-only по `created_at`) | **BRIN** — крошечный, но только при реальной корреляции |
| уникальность части строк | **partial unique** |
| хэш-равенство | **hash** — почти никогда; btree покрывает и сортировку тоже |

Порядок колонок в составном индексе решает: `(a, b)` обслуживает фильтр по `a` и по `a, b`, но **не** по одному `b`.

### Ловушка частичного индекса

**Частичный индекс применим только если запрос логически влечёт его предикат.** Не «в таблице всё равно нет удалённых строк», а буквально: в тексте запроса стоит условие, из которого предикат следует.

```sql
CREATE INDEX moves_order_line_id_idx ON moves (order_line_id)
  WHERE order_line_id IS NOT NULL AND deleted_at IS NULL;
```

```sql
LEFT JOIN moves m ON m.order_line_id = l.id                        -- индекс НЕ применится
LEFT JOIN moves m ON m.order_line_id = l.id AND m.deleted_at IS NULL -- применится
```

Цена ошибки: полный скан 2.25 млн строк вместо индексного поиска, 507 мс вместо 9.65 мс.

Где это возникает: **сырой SQL**. ORM для soft-delete сущностей дописывает `deleted_at IS NULL` к каждому джойну сам, а написанный руками запрос — нет. Поэтому проверять надо не весь код, а места с `manager.query`, вьюхи и миграции:

```bash
grep -rn "join <таблица>" src --include="*.ts" -i | grep -v deleted_at
```

## 4. Внешние ключи: индекс нужен на **дочерней** стороне

Postgres индексирует родительский ключ автоматически, дочернюю колонку — нет. Каждое `DELETE` или изменение ключа родителя проверяет ссылочную целостность, и без индекса это полный скан дочерней таблицы. Верно и для `NO ACTION`, и для `CASCADE`.

Детектор:

```sql
SELECT c.conrelid::regclass AS child_table, a.attname AS child_column,
       c.confrelid::regclass AS parent_table, c.confdeltype AS on_delete,
       EXISTS (SELECT 1 FROM pg_index i
               WHERE i.indrelid=c.conrelid AND i.indkey[0]=c.conkey[1]) AS has_index,
       pg_size_pretty(pg_total_relation_size(c.conrelid)) AS child_size
FROM pg_constraint c
JOIN unnest(c.conkey) WITH ORDINALITY AS k(attnum,ord) ON true
JOIN pg_attribute a ON a.attrelid=c.conrelid AND a.attnum=k.attnum
WHERE c.contype='f' AND array_length(c.conkey,1)=1
ORDER BY has_index, pg_total_relation_size(c.conrelid) DESC;
```

**Не чинить скопом.** Индекс дорожает каждую вставку в дочернюю таблицу, а горячая таблица на 800 МБ — это самый дорогой из возможных адресатов. Решение принимается по паре «размер дочерней таблицы × частота удаления родителя»: для многомегабайтной таблицы выигрыш очевиден, для таблицы в 16 КБ полный скан дешевле индекса. Двадцать индексов «на всякий случай» — это двадцать замедлений записи ради операции, которая случается раз в квартал.

## 5. Планировщик при многих джойнах

При числе отношений выше `join_collapse_limit` (умолчание **8**) Postgres перестаёт перебирать порядки соединения и выполняет джойны **в порядке, в каком они написаны**. При числе выше `geqo_threshold` (умолчание **12**) включается генетический оптимизатор — неполный перебор.

```sql
SELECT name, setting FROM pg_settings
WHERE name IN ('join_collapse_limit','from_collapse_limit','geqo','geqo_threshold',
               'work_mem','statement_timeout','random_page_cost','effective_cache_size');
```

Следствие для ORM: запрос с eager-связями на 15–20 таблиц пишется так, что корневая сущность идёт первой, а таблица с селективным фильтром — последней. Фильтр применяется после того, как всё уже сджойнено.

**Правильное лечение — не поднимать лимит, а перестать строить такой запрос.** Приём — пагинация в два шага (id-first):

1. узкий запрос без гидратации: посчитать `total` и выбрать id страницы;
2. второй запрос гидратирует связи **только для этих id**.

Поднятие `join_collapse_limit` до 20–24 — обезболивающее на один вечер: планирование дорожает, а следующая сущность с 25 связями упрётся снова.

## 6. Когда причина НЕ в индексе

Прежде чем добавлять индекс, исключить:

- **фильтр, который ничего не фильтрует.** `company_id` в однотенантной базе отбрасывает 0 строк и выглядит селективным. Проверять `count(*)` с фильтром и без;
- **устаревшую статистику.** `n_mod_since_analyze` сопоставимо с размером таблицы → план построен под старые объёмы. Лечится `ANALYZE`, а не индексом;
- **N+1.** Тысяча быстрых запросов вместо одного; в `pg_stat_statements` видна огромным `calls` при крошечном `mean`;
- **раздувание.** Мёртвые строки после массовых удалений; смотреть `n_dead_tup`, лечить `VACUUM`;
- **блокировки.** Ожидание, а не работа: `pg_stat_activity.wait_event_type='Lock'`;
- **клиентский таймаут.** Запрос успевает, но клиент уже ушёл. Признак — `(canceled)` в браузере ровно на круглой секунде вместо кода ответа от сервера.

## 7. Прод

**Только чтение.** `UPDATE`, `DELETE`, DDL агентом не выполняются: скрипт готовится, выполняет человек. `EXPLAIN ANALYZE` на `SELECT` допустим и полезен — это единственный способ получить настоящий план на настоящих объёмах.

Индекс на живой таблице создаётся **только** `CREATE INDEX CONCURRENTLY` — обычный `CREATE INDEX` держит блокировку записи на всё время построения. `CONCURRENTLY` не работает внутри транзакции, поэтому в миграции TypeORM требует отдельного шага; упавший `CONCURRENTLY` оставляет невалидный индекс, который надо снять и построить заново:

```sql
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
```

## 8. Замер до и после

Один и тот же запрос, одни и те же параметры, `BUFFERS` в отчёте. Сравнивать миллисекунды двух прогонов с разной прогретостью кэша — самообман; сравнивать страницы — нет.

Правку, меняющую текст запроса, **проверять на эквивалентность результата**, а не только скорости. Дешёвый способ — прогнать обе редакции по всем данным и сравнить множества в обе стороны:

```sql
WITH old_rows AS (<старый запрос без LIMIT>), new_rows AS (<новый запрос без LIMIT>)
SELECT (SELECT count(*) FROM (SELECT * FROM old_rows EXCEPT SELECT * FROM new_rows) d) AS only_in_old,
       (SELECT count(*) FROM (SELECT * FROM new_rows EXCEPT SELECT * FROM old_rows) d) AS only_in_new;
```

Ноль в обе стороны — правка ускоряет, не меняя ответа. Ненулевое — правка меняет поведение, и это отдельное решение, а не побочный эффект оптимизации.

## Приёмка

- [ ] окно `pg_stat_statements` проверено, `stats_since` записи сопоставлен с датой последнего выката;
- [ ] план снят с `BUFFERS`, а не только по времени;
- [ ] названа причина, а не симптом: сказано, **почему** индекс не применился или не помог;
- [ ] исключены неиндексные причины из §6;
- [ ] для частичного индекса показано, что запрос влечёт его предикат;
- [ ] для нового индекса под FK взвешена цена записи, а не только выигрыш удаления;
- [ ] замер до/после на одном контуре, в страницах;
- [ ] эквивалентность результата доказана, если менялся текст запроса;
- [ ] на прод не ушло ни одной записи от агента.

## Смежное

- `measurement-chain` — не меряет ли замер ограничение выше по цепочке.
- `code-config-driven` — поведение задают данные, вывод по коду является гипотезой.

## Границы данных

Прежде чем обратиться к среде за данными или сделать наполнители — скилл `data-boundaries`:
прод отдаёт конфигурацию и агрегаты, но не строки; наполнители генерируем сами по форме с
тестовых сред; выборка, которую не читают глазами, является выкачкой. Анкету с фиксированными
ответами печатает `~/.claude/harness/bin/run addons/data-boundary/answers.ts`, три класса блокирует гейт `data-boundary` харнесса.
